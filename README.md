# mail-tracker

Open and click tracking for personal 1:1 email, on a Cloudflare Worker.

## About this repository

This repository is the public part of a private agent harness. It carries the product intent, decisions and code; the tooling that writes, checks and reviews them stays private, so the method can be used here without disclosing private data. Agent configuration such as `CLAUDE.md`, `.claude/`, hooks and CI workflows is left out on purpose; please do not open pull requests adding it.

## How it works

- `src/` is a Cloudflare Worker (Hono on workerd) with a D1 database (`migrations/`).
  - `GET /i/<token>.png`: a transparent 1x1 PNG (`Cache-Control: no-store`) and one event row. Image URLs from older emails, without a suffix or ending in `.gif`, still work.
  - `GET /l/<token>`: a 302 to the https URL stored for that token, plus one event row. Destinations live only in D1 and are checked again on redirect (https, public host name, no credentials). A tracking URL never carries a destination or a recipient, and it can't be used as an open redirect.
  - Recording happens after the response, via `waitUntil`. A failing D1 write is logged and never breaks the image or the redirect. Every hit gets a row. A repeat by the same IP, user agent and HTTP method on the same image or link within 30s is flagged `duplicate` and left out of the counts, so a HEAD followed by a GET still counts the GET.
  - `POST /api/messages` (bearer `API_TOKEN`, the write token for the plugin) takes `{ "draftId", "subject", "recipient", "recipients": [addresses], "shared", "links": [https URLs], "linkText": { url: text } }` and returns `{ token, shared, recipients: [{ address, imageUrl, links: [{ url, redirectUrl }] }], imageUrl, links }`. Each address (compared case-insensitively) gets its own image and redirect tokens (ADR-0003). With `shared: true` (an account that sends one body to all, i.e. Microsoft Graph) there is one set: the recipient's own if there is one recipient, otherwise one with the address `""` (recipient unknown). The top-level `imageUrl` and `links` are message-level tokens for callers that send no `recipients`. It is idempotent per `draftId` (the draft's `headerMessageId`): calling it again updates the subject and recipients, reuses the tokens of known URLs and addresses, and adds tokens for new ones. Recipients that are no longer on the draft are kept but marked not current. It answers 201 the first time and 200 after that. `linkText` (optional) is each link's own text in the email, keyed by URL as in `links`. Whitespace is collapsed, text is cut to 200 characters, and text that only repeats a URL is dropped. A later registration without text for a link keeps the stored text. `draftTracked: true` (sent by `bun run compose`) marks a draft that carries its image and redirects before it is sent, so its earlier hits are draft previews (below); once set it stays set. `pixelToken` (sent by the plugin for such a draft) is the image token found in the draft: the registration then goes under the message that owns it rather than under `draftId`, and the answer adds `carried: { imageUrl, links: [{ url, redirectUrl }] }`, the redirects of that token set, and each set's `links` cover the links the draft already carries (ADR-0004). An unknown `pixelToken` is ignored.
  - `POST /api/messages/<token>/sent` (bearer `API_TOKEN`) takes `{ "sentAt" }` and records the delivery time once. A reported time before registration, or more than 5 minutes ahead of the Worker's clock, is replaced by the Worker's clock.
  - `GET /api/messages` and `GET /api/messages/<token>` (bearer `API_READ_TOKEN`, the read-only token for the owner's agent) are read-only summaries and per-email links and events, for the owner's agent. `GET /api/messages?unsent=1` lists every email not marked sent instead, events or not, each with `image_tokens` (every image token of the email), for `bun run sync-sent`. Events in the detail carry `label`, `via` and `preview` (1 for a draft preview, read with `counted` 0). The list shows emails that were sent or have events, with `recipients` and `opened_by` (current recipients with a counted open or click). Recipients removed from the draft are left out of both; the email page lists any that still have activity separately. The list also gives each email `addresses` (current recipients) and `reopens` and `last_reopen` (the re-open signal below). The detail adds `recipients` (opens, clicks, first and last open, re-opens and forwarding hints per recipient), a `name` on each link (see link names below), a `hint` on each event (see the forwarding hint below) and a `preloadHint` on each event (see the Gmail preload hint below).
  - `GET /api/tokens/<token>` (bearer `API_READ_TOKEN`) says what one image or redirect token stands for: `{ "message", "kind": "image" | "link", "recipient", "recipients", "url", "position" }`. `recipient` is the token set's address, or null for a shared set or a message-level token. `recipients` is the number of current token sets of the message with a known address. `url` is a redirect's destination, and `position` its place among the message's links (0-based, in order of first appearance); both are null for an image. An unknown token answers 404. The split-send gate uses it to check that every redirect in a recipient's copy goes where the owner's copy says, and belongs to that recipient. Token rows never change once minted: the database refuses an UPDATE of a token's destination, set, address or position (migration 0005).
  - `GET /api/people` and `GET /api/people/<address>` (bearer `API_READ_TOKEN`) are the people view, described under `/app/people` below. The person route answers 404 for an address on no listed email.
  - `/app` is the dashboard: a list of emails (with how many recipients opened), and a page per email with its totals (opens split into probable human and on-open proxy, clicks per link, first and last open), a row per recipient, and the full timeline with the recipient of each event. Recipient cells link to that person's page. Every page refreshes every 15s while the tab is visible. Cloudflare Access protects it. The Worker verifies the `Cf-Access-Jwt-Assertion` header against the team's keys, issuer and audience, and requires `exp`. If `ALLOWED_EMAILS` is set, the token's email must be one of them. An unknown key id triggers a refetch of the keys, for key rotation, at most once a minute, so made-up key ids sent to `/i/` and `/l/` cannot make the Worker fetch keys on every hit.
  - `/app/people` lists one row per recipient address across all listed emails: last activity (the default sort, newest first), last open, last click, last re-open, emails sent, emails opened (a counted open or click), and the median time from sending to the first counted open (a probable human or an on-open proxy such as Gmail's; Apple's prefetches are not counted). It can be searched by address and filtered by status (opened, not opened, clicked, re-opened). `/app/people/<address>` shows the same figures for one person and their emails with that person's own status, opens, clicks and re-opens. It is sorted by latest activity, newest first, and can be filtered the same way. Only current recipients with a known address are people. A shared copy to several recipients (Graph) and emails from before per-recipient tokens are on no one's page. The data comes from `/app/people/data` and `/app/people/<address>/data` (`src/people.ts`).
  - The dashboard is a React app in `web/` (Vite, Tailwind), built into `web/dist/app` and bound as Workers Static Assets (`ASSETS`). `run_worker_first` sends every request, assets included, through the Worker, so the page, its script, styles and fonts are only served after the Access check. The app reads JSON from `/app/data` and `/app/messages/<token>/data` (shapes and the counting rule: `src/dashboard-data.ts`). All of it is served with a strict CSP: same-origin script, styles, fonts and images only, no inline script, no third-party origins.
  - The app uses the LittleBit Bauhaus design system ([yuriyward/bauhaus-design-system](https://github.com/yuriyward/bauhaus-design-system)). The copied files are listed with their source in `.ward/design-system-copies.tsv`, and the design-system commit they match is in `.ward/design-system-base`. They are left exactly as copied and are excluded from lint and format.
  - There are no CORS headers. `/api` is for the plugin (Node `https`) and agents, not for browsers.
- Every event is kept raw and classed `human` (probable human), `proxy` (proxy or prefetch), `scanner`, `self` or `unknown`, with the reason stored (`src/classify.ts`):
  - **self**: an IP in `SELF_IPS`, or a valid Access token of the owner (header or `CF_Authorization` cookie, verified like `/app`). A cookie that is merely present, or a Mailspring user agent, does not count.
  - **scanner**: HEAD requests, bot user agents, hits from a security gateway's published ranges (below), clicks within 10s of sending, clicks from data-centre networks, and the same IP and user agent clicking two links of the email within 3s. Your own clicks are left out of that check.
  - **proxy**: on-open image proxies (Gmail's `GoogleImageProxy`, Yahoo's, or an open from Google's published service ranges), and prefetches (Apple's bare `Mozilla/5.0`, an open from Apple's Private Relay or Microsoft's Exchange Online ranges, mail-provider networks, opens within 30s of sending).
  - **Published network ranges** (`src/networks.ts`): the hit's IP is looked up in the vendors' own lists, and the reason names the list that matched, e.g. `prefetch: IP in the Apple iCloud Private Relay egress list`. The first list that holds the IP decides:

    | List | Source | Open | Click |
    | --- | --- | --- | --- |
    | Apple iCloud Private Relay egress (Mail Privacy Protection loads images through it) | [egress-ip-ranges.csv](https://mask-api.icloud.com/egress-ip-ranges.csv) ([docs](https://developer.apple.com/support/prepare-your-network-for-icloud-private-relay/)) | prefetch | other rules (people browse in Safari through the same relay) |
    | Google services, Gmail's image proxy among them | [goog.json](https://www.gstatic.com/ipranges/goog.json) minus [cloud.json](https://www.gstatic.com/ipranges/cloud.json), Google Cloud customers ([docs](https://support.google.com/a/answer/10026322)) | on-open proxy (counted) | scanner |
    | Microsoft 365 Exchange Online and Exchange Online Protection, where Defender for Office 365 Safe Links runs | [endpoints.office.com](https://endpoints.office.com/endpoints/worldwide?clientrequestid=b10c5ed1-bad1-445f-b386-b919946339a7), service area Exchange ([docs](https://learn.microsoft.com/en-us/microsoft-365/enterprise/urls-and-ip-address-ranges)) | prefetch (Outlook's image proxy is still counted by its user agent) | scanner |
    | Mimecast | SPF records under `_netblocks.mimecast.com` ([Data Centers & URLs](https://mimecastsupport.zendesk.com/hc/en-us/articles/34000362728979-Administration-Data-Centers-URLs)) | scanner | scanner |

    The ranges are a committed data file, `src/networks.json`, that `bun run refresh:networks` regenerates from these sources. Review the diff, commit, deploy. A file was chosen over a cron trigger that writes them to D1 or KV because it needs no binding, migration or per-hit query, keeps classification a pure function that tests can pin down, and the lists change slowly. Apple's 285k prefixes collapse to about 14k blocks (450 KB, about 200 KB gzipped in the bundle). The cost is that new ranges only apply after a refresh and deploy.

  - **Counting:** opens and clicks in the list count only probable humans and on-open proxies, without duplicates, so an Apple prefetch is never shown as the first open. The timeline shows every event.
  - **Labels:** the timeline and the read API (`label`, `via` on each timeline event) show plain labels instead of class names (`eventDisplay` in `src/classify.ts`). A probable human, and an on-open image proxy, is "Opened" or "Clicked"; the proxy also names its client, e.g. "Opened via Gmail" for Gmail's `GoogleImageProxy` (every Gmail open arrives that way, from Google's IPs). The rest of `proxy` is "Prefetch" (Apple Mail Privacy Protection or Private Relay, Exchange Online, mail-provider networks, opens seconds after send). `scanner` is "Scanner", `self` is "You", `unknown` is "Unknown"; these and "Prefetch" are muted. The stored class and counting are unchanged: an on-open proxy is told apart from a prefetch by its stored reason, which always starts with `on-open image proxy`, so no migration was needed. The class filter uses the labels; the badge's tooltip shows the stored reason.
  - **Draft preview** (ADR-0004): an email composed with `bun run compose` carries its image and redirects in the draft, so showing the draft (in the composer, a draft list, on the phone) hits the Worker. For such an email, an event before `sent_at`, or any event while `sent_at` is unset, is labelled "Draft preview" (muted) and is not counted anywhere: not in opens or clicks, first open, opened by, re-opens, the people view, or as the forwarding hint's first event. The raw row is kept and the rule is applied when read, so once `sent_at` is set, earlier events stay previews and an open between the real send and the moment `sent_at` was reported counts. Emails tracked by the plugin alone only get the image at send, so their events count as before.
  - **Re-open signal** (`src/reopen.ts`): within one recipient's token set, a counted open (a probable human or an on-open image proxy such as Gmail's `GoogleImageProxy`, not a repeat) is a re-open when it comes long enough after that set's previous counted open. A probable human needs an hour or more, an on-open proxy six hours or more (owner decision, 2026-11-12), and a hit marked "possibly preloaded by Gmail" (below) is never a re-open. It does not reset the gap either: the next open is measured from the previous unmarked one, so a preload cannot hide a later real re-open. The email, the recipient row, the person and the timeline event show "re-opened" with when. The email list can filter by it and sort by last re-open. An on-open proxy fetches the image only when the recipient opens the email, so a Gmail recipient can show as re-opened (owner decision, 2026-11-11). Prefetches (Apple Mail Privacy Protection, Private Relay, Exchange Online), scanners and your own hits are not counted, so they neither start nor resume a run. A proxy that caches the image would hide later opens. It is worked out when the data is read and does not change any count. For the email's own signal, only current recipients and message-level tokens count, as in the list.
  - **Gmail preload hint** (`src/preload.ts`): opening one email in Gmail can make Gmail's image proxy fetch the image of another email to the same person as well. Live, two emails to one Gmail address were fetched in pairs 0 to 12 s apart when only one was opened. The proxy's request is the same for an open and a preload, and a person searching their mail can really open several emails in a row, so nothing is dropped. When two different emails to the same address get on-open Gmail proxy hits within 15 s of each other, the later hit gets the badge "possibly preloaded by Gmail". Its tooltip and the event's `preloadHint` say why. Both hits still count as opens, and both emails as opened, but the marked hit never counts as a re-open (owner decisions, 2026-11-12). Only current recipients with a known address are compared. It is worked out when the data is read from the stored rows, which are not changed.
  - **Link names** (`src/link-names.ts`): a link is shown by its own text in the email, which the plugin sends at registration, or else by its domain without `www.` or `m.` (`cal.com`, `linkedin.com`, `github.com`). The full URL is in the tooltip. Emails registered by an older plugin have no text, so their links show the domain.
  - **Forwarding hint** (`src/forwarding.ts`): within one recipient's tokens, a later probable-human event from a different network, country or kind of device (phone, tablet, computer) than that recipient's first one is marked "possibly forwarded or opened by someone else", with what differed. It is worked out when the data is read and does not change any count. It is a hint, not proof: the same person on mobile data or a second device looks the same. Shared copies to several recipients and emails from before per-recipient tokens get no hint.
- `mailspring-plugin/` tracks at send time, in two steps, because Mailspring calls `applyTransformsForSending` synchronously and serialises the body right after (`app/src/flux/tasks/send-draft-task.ts`):
  1. **While you compose:** an invisible `Composer:Footer` component sees each edit of a draft that is open in a composer. Drafts that only arrive by sync are never registered. The window showing the composer registers the draft with the Worker 2s after the last edit, keyed by its `headerMessageId`, and again right when you press Send. Only https links outside quoted text (`.gmail_quote`) are sent, each with its text (an image-only link sends its `alt` text) so the dashboard can name it. Editing only a link's text registers the draft again. Bare `https://` URLs typed as plain text are first turned into links (both here and at send), so their clicks go through the Worker too. Without this, the recipient's client (Gmail, iOS Mail) makes them clickable itself and the click bypasses tracking. Text inside existing links, quoted text (`.gmail_quote`, `blockquote`), `code` and `pre` is left alone. Trailing punctuation (`.,;:!?)]` and quotes) is not part of the URL. Only URLs the redirect allow-list accepts become links. Your Sent copy keeps the text as you typed it. The tokens are stored in Mailspring's local config, one key per draft (`mail-tracker-registrations.<draft>`). Each write touches only its own key, so windows never overwrite each other, and every window can read them, so it also works with undo send and send later.
  2. **At send:** `needsPerRecipientBodies` makes Mailspring file the untransformed body as your Sent copy, so it has no image and no rewritten links, and run the hook once per recipient. Each run uses that recipient's tokens: it rewrites only the links already registered and adds the image before any quoted text, marked up like Mailspring's own (`<img alt="" src="….png">`, no size, style or class, which blockers look for). It replaces tracking images quoted from earlier emails. Links added after the last registration, and drafts never registered, go out as written. The tokens are used only if the registration covers exactly the draft's current recipients (compared case-insensitively, in any order) and the same delivery mode (one shared body under Graph, or one body each). Otherwise the whole email goes out untracked and the console logs why once, so no one gets another recipient's tokens. It is still one message row per draft. If the draft as sent has links or a subject or recipients that the registration doesn't cover, it logs a warning once (`mail-tracker: sending with an older registration: …` in the console).
  3. **After delivery:** only when Mailspring reports delivery (`draftDeliverySucceeded`, in the main window) does the plugin mark the email sent, with the delivery time. A failed delivery never sets the send time. The notice is kept in config (`mail-tracker-pending-sent`) and retried after 10s, 1min, 5min, 30min and 2h, including after a restart. After that it is dropped and logged.
  - **Drafts an agent composed with tracking** (ADR-0004): when the draft already holds our image (the same Worker origin, outside `.gmail_quote` and `blockquote`), the plugin registers it with `pixelToken`, so it joins the agent's message rather than creating a second one, and stores the carried redirects. At send, the draft's image is replaced, never doubled. With several recipients and one body each, each recipient's body gets that recipient's own image and redirects in place of the agent's shared ones. With one recipient, or one shared body under Graph, the set is the agent's own and the tokens stay as they were. Links the owner adds in Mailspring are registered and tracked as usual. Delivery is reported as above. If the draft was never registered or its recipients changed since, it goes out as the agent wrote it.
  - **Never blocks a send:** plaintext drafts, a disabled or unconfigured plugin, and any error inside the hook all mean the mail goes out untracked.
  - Requests go through Node's `https`, not `fetch`. Mailspring windows load from `file://` with web security on, so a `fetch` with an `Authorization` header would need a CORS preflight.

## Agent drafts

The owner's agent writes the email and creates the draft through its own mail tools. This repository renders and tracks it, and never creates drafts, reads mail or sends anything (ADR-0004).

```bash
export MAIL_TRACKER_URL=https://track.example.com
export MAIL_TRACKER_API_TOKEN_FILE=~/.config/mail-tracker/api-token        # the write token
export MAIL_TRACKER_READ_TOKEN_FILE=~/.config/mail-tracker/read-token      # for sync-sent

bun run compose --to alex@example.com --subject "Proposal" \
  --body-file .tmp/proposal.md --template ~/.config/mail-tracker/template.html \
  --out exports/compose/proposal
```

- **`bun run compose`** takes `--to`, `--cc`, `--bcc` (repeatable or comma-separated, `Name <address>` accepted), `--subject` and `--body-file`. A `.md` file, or `--markdown`, is Markdown; anything else is plain text. Either way the body keeps its lines as written: a single newline is a line break (`<br>`; Markdown in "breaks" mode) and a blank line a paragraph, while Markdown links, emphasis, lists and code still work. Raw `<script>`, `<style>` and `<iframe>` in Markdown are shown as text. `--template` is an HTML file with one `{{body}}` slot, for example with the owner's signature; the default is `src/cli/template.html` (or `MAIL_TRACKER_TEMPLATE`). Bare https URLs become links, as in the plugin. The email is registered and the image and redirects are put in: one recipient gets that recipient's token set, several get one shared set ("shared copy, recipient unknown"). It writes `body.html`, `body.txt` (the text alternative: the body's lines exactly as written, except that a Markdown `[text](url)` becomes `text (url)`, then the template's text, where links show their real destination) and `receipt.json` to `--out` (default `exports/compose/<time>`) and prints the receipt: `status` (`tracked` or `untracked`), `token` (the message token), `draftId`, `shared`, the recipients, `imageUrl` and `links`. `--no-track` renders the same email without registering it, with no image and the links as written. Tokens come from `MAIL_TRACKER_API_TOKEN` or the file in `MAIL_TRACKER_API_TOKEN_FILE` (or `--token-file`), never from the command line. `MAIL_TRACKER_URL` (or `--url`) must be https; plain http is accepted only for `localhost`, `127.0.0.1` and `[::1]`, for a local Worker.
- **`bun run compose --per-recipient`** is for sending one copy per recipient with the same To and Cc headers, as Mailspring does (ADR-0004 note 2026-11-12; the sending itself is fastmail-cli's). It registers one email with a token set per address and writes, instead of `body.*`, `recipients/<i>/body.html` and `body.txt` (recipient i's own image and redirects), `self/body.html` and `body.txt` (the owner's copy: no image, each tracked link at its destination as the Worker stores it, in the same order as in the recipients' copies) and `receipt.json`: `mode: "per-recipient"`, `token`, `draftId`, the recipients, `links` (the tracked destinations in token order) and `items: [{ i, address, role, imageToken, linkTokens }]`. `i` counts from 0 in To, Cc, Bcc order, and `linkTokens[k]` redirects to `links[k]`. The text alternative carries no tracking, so it is the same in every copy. An address given twice, in any header or case, is refused, and `--no-track` cannot be combined with it. `sync-sent` cannot match the owner's copy, which carries no image, so the sender marks the email sent with `POST /api/messages/<token>/sent`.
- **Sending** from Mailspring gives each recipient their own tokens, as above, and files a clean Sent copy: the plugin takes the agent's image out of the body Mailspring files as `self` and maps each carried redirect back to its URL using the `carried` map it got at registration (never by guessing), so reopening your own Sent mail records nothing. An earlier email's image or redirect in quoted text is kept. If the registration no longer fits (recipients or delivery mode changed), nothing is split or cleaned: the draft goes out, and is filed, as the agent wrote it. If Mailspring's own open or link tracking is switched on for the draft, Mailspring may not ask this plugin whether to use separate bodies, so the Sent copy is not cleaned. Sending from anywhere else (Fastmail web, the phone) sends the draft as it is: with several recipients that is one shared copy, and the Sent copy keeps the image and redirects (see Known limits).
- **`bun run sync-sent`** marks emails sent from outside Mailspring. The agent pipes the owner's recently sent messages in as JSON, `[{ "subject", "recipients": [...], "sentAt": ms or ISO date, "html" }]`. Each message is matched by our image token in its HTML, outside quoted text, to an email that is not marked sent (`GET /api/messages?unsent=1`), and its `sentAt` is reported. The report lists each message with a `status`: `marked`, `duplicate` (the email was already matched by an earlier message of the input), `unmatched`, `invalid` (`sentAt` is not a date) or `failed` (the Worker's `httpStatus` is given). It exits 1 when any failed or was invalid. Running it again changes nothing, since the Worker keeps the first send time. It needs both tokens: the read token to list, the write token to mark.
- Until an email is marked sent, every hit on it is a draft preview and not counted (see **Draft preview** above). Run `sync-sent` after the owner sends.

## Quick start

Requires [Bun](https://bun.sh) and a Cloudflare account with your domain on it.

```bash
bun install
bun run check
```

1. **Create the database** in the EU jurisdiction and paste the printed `database_id` into `wrangler.toml`:

   ```bash
   bun x wrangler d1 create mail-tracker --jurisdiction eu
   bun x wrangler d1 migrations apply mail-tracker --remote
   ```

2. **Choose the host.** In `wrangler.toml`, uncomment `routes` and set your subdomain, e.g. `track.example.com`. `workers_dev` stays off.

3. **Protect the dashboard.** In Cloudflare Zero Trust, add a self-hosted Access application for `track.example.com/app` with a policy that lets only you in (the Worker refuses any `/app` request without a valid Access assertion, so a path Access misses fails closed). Put the team domain (`<team>.cloudflareaccess.com`) in `ACCESS_TEAM_DOMAIN` and the application's AUD tag in `ACCESS_AUD` in `wrangler.toml`. Do not put `/i/` or `/l/` behind Access.

4. **Set the API tokens** (long random strings): `API_TOKEN` is the write token for the plugin, and `API_READ_TOKEN` is the read-only token for your agent. Neither works for the other's routes.

   ```bash
   openssl rand -base64 32 | bun x wrangler secret put API_TOKEN
   openssl rand -base64 32 | bun x wrangler secret put API_READ_TOKEN
   ```

   Optionally list your own IPs in `SELF_IPS` so your hits are classed self, and your Access email in `ALLOWED_EMAILS`.

5. **Deploy:** `bun run deploy` (wrangler builds the dashboard app first, `bun run build:web`).

6. **Install the Mailspring plugin:**

   ```bash
   bun run build:plugin   # writes mailspring-plugin/lib/main.js
   ```

   In Mailspring choose _Developer → Install a Plugin…_ and select the `mailspring-plugin` folder (or link it into Mailspring's `packages` directory). Open _Preferences → Mail Tracker_, enter the Worker URL (`https://track.example.com`), the write API token (`API_TOKEN`) and the read API token (`API_READ_TOKEN`), and keep _Track opens and clicks_ on. Turn off Mailspring Pro's own read receipts and link tracking so a message is not tracked twice.

To run the Worker locally: `bun x wrangler d1 migrations apply mail-tracker --local`, put `API_TOKEN=...` and `API_READ_TOKEN=...` in `.dev.vars` (ignored by git), then `bun run dev`. Locally there is no Access in front, so `/app` answers 401 unless you send a valid assertion. `bun run build:web` rebuilds the app, and `bun run check` builds it before the tests that inspect the build.

### Read status in Mailspring

The plugin registers in the same `ThreadListIcon` and `MessageHeaderStatus` slots as Pro. The thread icon shows the most recent tracked outgoing message in the thread (including after an untracked reply); the header shows that message's own status. Both show opens and clicks; the header separates human and proxy opens. Hover shows the native summary tooltip. Click (mousedown, as in Pro) opens a 360px-wide, vertically scrollable panel using Mailspring’s standard popover dismissal, with per-recipient totals, event times, country, device user agent, the API's labels, proxy client, forwarding/preload hints and clicked link names and destinations. Shared copies explicitly say “Shared copy, recipient unknown”; removed recipients are marked separately. Opens remain signals, not proof of reading.

Enter the **Read API token** next to the write token in Preferences → Mail Tracker. Reads use HTTPS with `Authorization: Bearer <read token>` through Node (no renderer CORS preflight). Reads never block rendering: missing configuration, untracked mail, rejected/malformed responses and offline errors render nothing. Endpoint responses and failures are cached for 60 seconds per window and configuration; visible components refresh every 60 seconds and on window focus, respecting that cache. No notifications or Worker deployment are involved.

A saved registration maps the sent message's `headerMessageId` to its message token, including Mailspring's clean Sent copy. Without a registration, only a message in a Sent category is inspected: its body is loaded asynchronously if necessary, and a same-origin `/i/<token>.png` or `/l/<token>` outside quoted text is resolved with `GET /api/tokens/<token>`. A clean copy from another sender has no such identity and shows nothing. Existing registration housekeeping removes records after 30 days; a clean copy whose registration has expired also shows nothing. The client supports cached `GET /api/messages` list reads and uses `GET /api/messages/<token>` for the full status and event panel.

## Limits

- Opens and clicks are hints, not proof: Apple Mail Privacy Protection prefetches images, Gmail proxies them, and security gateways follow links. Check the class and reason of each event.
- Classification happens once, when the event arrives; a later burst does not reclassify earlier clicks.
- **Published ranges go stale** between refreshes (`bun run refresh:networks`), and they only cover what each vendor publishes. Microsoft does not publish separate ranges for Safe Links detonation, which can run from wider Azure space. Mimecast's and Proofpoint's lists are their mail-server ranges, so their link scanners may use other addresses. Proofpoint Enterprise (Proofpoint on Demand) publishes no general list. Proofpoint's page is not machine-readable, so its ranges are copied by hand.
- The plugin stores both API tokens in Mailspring's config file in plain text.
- Links in quoted text are left as they are, so tracked links quoted from an earlier email keep crediting that email.
- A link added, or a draft written, in the last moment before Send may go out untracked if its registration has not finished. Mailspring does not wait for it.
- Registrations are kept in Mailspring's config for 30 days; the main window prunes older ones on start-up.
- **Graph accounts** (Microsoft accounts that Mailspring sends through Microsoft Graph, detected with `account.sendsViaGraph()`): Mailspring sends one tracked body to all recipients, so the plugin registers one shared token set. With several recipients the dashboard shows "shared copy, recipient unknown". If the delivery mode at send differs from the registration's (an account switch that has not re-registered yet), the email goes out untracked rather than credit one person for everyone. Treat the Sent copy as tracked: it may keep the image and rewritten links, and opening it records events, classed self only if your IP is in `SELF_IPS`. Mailspring's source says its untracked `self` body is still filed as the Sent copy for these accounts, but this is unverified, and Microsoft may file the tracked message as well.
- Drafts registered by the plugin before per-recipient tokens register again the next time a composer shows them. One sent without being opened in a composer again goes out untracked.
- **Agent drafts** (ADR-0004): links the owner adds outside Mailspring stay untracked, and a send with several recipients from outside Mailspring is one shared copy. Sent from Mailspring, the Sent copy is clean (no image, original links). Sent from Fastmail web or the phone, the Sent copy keeps the image and redirects, so opening it later counts as the recipient's open unless your IP is in `SELF_IPS` or the hit carries your Access token; the Worker cannot tell such an open from the recipient's, so list your home and phone IPs in `SELF_IPS` or open those Sent copies sparingly. `sync-sent` cannot match a clean Mailspring Sent copy, since it has no image; those emails are marked sent by the plugin on delivery instead. Until `sync-sent` reports the send time, the "seconds after send" rules (early opens and clicks) measure from registration, so they cannot fire for such an email; prefetches are still caught by their published ranges and user agents. Whether Fastmail and iOS Mail keep the draft's HTML unchanged on send has not been checked.
- **Scanners that rotate IPs** still create one row per hit. Duplicates are only recognised for the same IP, user agent and method. Scanner rows are classed but not counted, and they count towards D1's write limits.
